# d750d: the daemon that owns the radio's serial port

## What it is for

d750d is the only program that opens the TM-D750's serial port. Every other tool in this project,
and every Hamlib program you point at the radio, talks to d750d over a local network port instead.
That keeps two programs from fighting over one port, and it lets d750d enforce the safety rules
below in one place. (A daemon is a program that runs in the background. See the
[glossary](glossary.md) for other terms on this page.)

d750d runs as a systemd user service. systemd is the Linux service manager, and a user service is
one it starts for you, not for the whole machine. [Install](install.md) sets it up.

## Before you start

- The radio is on and its USB cable is plugged in. The radio shows two USB serial ports. d750d opens
  `/dev/d750-cat`, which is the control head's port (USB id 2166:9030). The other port, the base
  unit's (USB id 2166:9032), is `/dev/d750-tnc` and belongs to [d750-aprs](aprs.md). The udev rule
  (`config/60-d750ctrl.rules`) creates both names. udev is the part of Linux that names devices when
  you plug them in. `sudo ./install-udev.sh` installs the rule once. See [Radio
  setup](radio-setup.md).
- The radio's CAT port must carry only CAT. CAT is the radio's command language over the serial
  port. GPS sentences on that port slow every command to seconds. Set menu 403 to Off, or run
  `d750 gps output off`.

## Try it

The sample output on this page was captured from the simulator, a pretend radio, not from a real
one. See [Try it without a radio](try-without-a-radio.md).

Ask the daemon what it is doing:

```sh
d750 state
```

```text
port open /dev/pts/0; not keyed; unlocked; last answer 18:48:20; unsolicited bytes seen 0
```

On a real radio the port is `/dev/d750-cat`. Send one Kenwood command through the plain command
port:

```sh
d750 raw ID
```

```text
ID TM-D750
```

Try a command the daemon refuses on that port:

```sh
d750 raw TX
```

```text
ERR TX is not allowed on this port; keying goes through 4532
```

Stop all keying, then allow it again:

```sh
d750 lock
d750 unlock
```

```text
OK locked, PTT refused until unlock
OK unlocked
```

Read the daemon's log:

```sh
d750 log 12
```

```text
18:48:21 cmd 'SQ 1,4' -> 'SQ 1,4'
18:48:21 cmd 'PC 0,2' -> 'PC 0,2'
18:48:24 cmd 'TN 0,1' -> 'TN 0,1'
18:48:24 cmd 'TN 2,1' -> 'TN 2,1'
18:48:24 cmd 'ME 002' -> 'N'
18:48:25 unkey in 21 ms, radio said 'RX'
18:48:25 cmd client ('127.0.0.1', 59438): refused 'TX'
```

(That is a trimmed copy of a longer log.) To check the service itself:

```sh
systemctl --user status d750d
```

## What it can do

d750d has no command line arguments and no help text. It is configured with environment variables
(see Settings below) and it starts with `python3 -I d750d.py`. Both of its ports listen on
`127.0.0.1` only, so nothing outside your computer can reach them.

### Port 4532: hamlib's NET rigctl protocol

Hamlib is a library that many radio programs use to control radios. Its NET rigctl rig speaks to a
rigctld server over the network, and d750d acts as that server. Programs such as xara, WSJT-X,
fldigi, GridTracker and OpenSlot, and any other Hamlib-aware program, can tune and key the radio
through it.

To point a program at it:

- Choose the rig "NET rigctl". On the command line that is rig model 2, as in
  `rigctl -m 2 -r 127.0.0.1:4532 f`, which prints the transmit band's frequency in hertz.
- Give it the address `127.0.0.1:4532`.

What d750d answers on this port:

- The opening handshake: `chk_vfo` and `dump_state`.
- Frequency: `f` and `F`. Mode: `m` and `M`. VFO: `v` and `V`. Keying: `t` and `T`. Split: `s` and
  `S` (accepted, with no effect). Levels: `l` and `L`.
- `get_vfo_info`, `get_powerstat` (always on), `get_lock_mode` (always unlocked), and the long names
  of the same commands, such as `get_freq`.
- VFOA is band A. VFOB is band B. The current VFO is the band that transmits.
- Modes are FM, FMN (narrow FM), AM and DSTAR. The names PKTFM and WFM are taken as FM, NFM as FMN,
  DV as DSTAR and PKTAM as AM.
- Levels are STRENGTH, RAWSTR, RFPOWER and SQL. RFPOWER reads as 1.0 for high, 0.5 for mid, 0.2 for
  low and 0.1 for EL. Setting it picks the nearest of those four. SQL is the squelch level from 0 to
  1.
- The frequency, mode and level commands act on the band that transmits. Setting the VFO with `V`
  changes which band transmits, so a program that selects VFOA or VFOB moves transmit to that band.
- `T 1` keys the radio, `T 0` unkeys it, and each is answered with `RPRT 0`.

### Port 4533: the plain command port

This port takes one Kenwood command per line and returns the radio's one-line answer, or `ERR` and a
reason. The [d750 verbs](d750.md) and the [rig screen](d750ctrl.md) use it, and so does d750-aprs.

It also understands five words of its own:

- `state`: the one-line state shown above.
- `lock`: refuse keying until `unlock`. If the radio is keyed, `lock` unkeys it first.
- `unlock`: allow keying again.
- `reconnect`: close the serial port and open it again.
- `quit`: end this connection.

### What it refuses

- Port 4533 never passes these commands to the radio: `TX` (key), `RX` (unkey), `UP` and `DW` (the
  microphone's up and down keys), `SR` (reset the radio), `PS` (power off), `0M` (programming mode)
  and `0G` (service mode). The answer is `ERR` and a reason. Only port 4532 may key, and only with
  `T 1` and `T 0`.
- While the daemon is locked, `T 1` on port 4532 is refused with `RPRT -1`.
- A frequency, mode or level the radio itself refuses (it answers `N` or `?`) is an error to the
  client, and is logged.

### When it unkeys by itself

d750d unkeys the radio:

- when it starts;
- when a client on port 4532 disconnects while the radio is keyed;
- when the serial port gives an error;
- when you send `lock` while the radio is keyed;
- 30 seconds after the radio was keyed, whatever the client does. A program that needs to transmit
  longer must send `T 1` again at least every 30 seconds. d750-sstv and d750-rtty do it every 15
  seconds;
- when you stop the daemon from a terminal with Ctrl+C.

`d750 ptt off` unkeys at once, by sending `T 0` to port 4532.

### What it logs, and where

The log is `~/.local/share/d750ctrl/log/d750d-YYYY-MM-DD.txt`, with one file per day, and every line
starts with the time. d750d also prints each line to its own output, which
`journalctl --user -u d750d` shows. It logs:

- keying and unkeying, with the milliseconds the radio took to answer;
- every command that changes the radio, and every command the radio refused;
- commands refused on port 4533;
- errors, and the serial port opening and closing;
- bytes the radio sends without being asked. An APRS packet printed on the CAT port is logged as one
  line, "APRS packet on the CAT port", and dropped. Other unasked bytes are logged as a count and
  the first 40 bytes, and discarded.

It leaves out the routine reads the radio answered, such as the frequency or the busy flags. The
same error again is logged once, and then counted: one line a minute says how many more there were.
After a quiet minute the next one is logged in full again. Set `D750_LOG_ALL=1` to log every
exchange.

## Settings

d750d reads no settings file. These environment variables change it, and the list is the whole
interface:

- `D750_PORT`: the serial device. Default `/dev/d750-cat`.
- `D750_PTT_PORT`: the Hamlib port. Default `4532`.
- `D750_CMD_PORT`: the command port. Default `4533`.
- `D750_LOG_DIR`: the log folder. Default `~/.local/share/d750ctrl/log`.
- `D750_BAUD`: the serial speed. Default `9600`.
- `D750_LOG_ALL`: any value except empty, `0`, `no`, `off` or `false` logs every exchange. Default
  is off.

The service file that `install.sh` writes sets none of them. The tests set them to run a second
daemon on ports 4542 and 4543 against the simulator. To set one for the real service, use a systemd
drop-in (`systemctl --user edit d750d`, then add an `Environment=` line), because `install.sh`
rewrites the service file each time it runs. The other tools find the ports from `ptt_port` and
`cmd_port` in `d750ctrl.conf`; see [Settings](settings.md).

## When something goes wrong

- **You see:** `ERR d750d is not answering on 127.0.0.1:4533 (systemctl --user status d750d)`, or
  the rig screen says "Fail: d750d is not answering".
  - **Why:** the daemon is not running.
  - **What to do:** run `systemctl --user status d750d`. Start it with
    `systemctl --user start d750d`, and read `journalctl --user -u d750d` if it stops again.

- **You see:** `radio port not available` in answers, or "serial port closed" in the log.
  - **Why:** the radio is off, the cable is out, or `/dev/d750-cat` is missing because the udev rule
    is not installed. d750d starts without the radio and opens the port when it appears.
  - **What to do:** run `d750 doctor`. Check the cable and run `sudo ./install-udev.sh` if the name
    is missing. After the radio is back, `d750 fixup` puts back the settings the tools rely on.

- **You see:** every command takes seconds, or `d750 doctor` says "unsolicited bytes on the CAT
  port".
  - **Why:** the radio is sending GPS sentences, or other bytes nobody asked for, on the CAT port.
  - **What to do:** set menu 403 to Off (or check menu 982), or run `d750 gps output off`.

- **You see:** `RPRT -1` when a program tries to key, or "locked: PTT refused" in the log.
  - **Why:** the daemon is locked.
  - **What to do:** run `d750 unlock`. Lock it again with `d750 lock` whenever you want no
    transmitting.

- **You see:** the radio unkeys by itself after 30 seconds.
  - **Why:** that is the watchdog. See "When it unkeys by itself".
  - **What to do:** have the program send `T 1` again within every 30 seconds.

- **You see:** the radio and everything else on the USB bus drop out, or the radio restarts.
  - **Why:** a transmitting handheld near the USB leads can reset the bus. After the radio restarts,
    its TNC may take commands but send nothing.
  - **What to do:** keep transmitting handhelds away from the leads. See [d750-aprs](aprs.md), which
    resets the TNC after the radio comes back, and [Troubleshooting](troubleshooting.md).
